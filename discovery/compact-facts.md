# Краткие факты для быстрого просмотра компаний

При discovery/enrichment и анализе новых/изменённых вакансий в monitoring, после чтения первичного материала сохранять полные ответы по критериям и при полезности добавлять observation.short_facts: до трёх строк по 100 символов. Это сокращения того же ответа, с теми же scope/evidence, а не отдельные бездоказательные оценки. Поле необязательно; старые импорты research 1.0 работают без него. Пустой ответ/отсутствие evidence не допускают short_facts. UI показывает только прошедшие содержательный review, не устаревшие и не конфликтующие сведения; строка может быть короче лимита, но не ценой потери существенного ограничения.

## Как выбирать содержание

- **B04, без role/job_url → Описание бизнеса:** сегмент и подтверждённая монетизация: `B2B · SMB`, `Подписка`, `Комиссия с заказа`. Тип Gaming/Marketplace уже виден в компании — не дублировать его без дополнительного смысла. Нельзя выводить подписку только из слова SaaS или размер комиссии из категории бизнеса.
- **B04 или AN06, с role/job_url → Целевые вакансии:** предмет работы и решения: `B2B retention / renewals`, `Growth / acquisition`, `Pricing`, `Operations / CX`, `BI / reporting`. Не заменять задачи всей компании задачами одной роли. North Star не выводить из перечня рабочих метрик. Не размечать фокус по одному заголовку вакансии: прочитать обязанности.
- **A05 → Целевые вакансии:** конкретное ограничение формата: `Remote · только ES`, `Офис 3 дня/нед.`, `EU time zones`. «Только» — при прямом ограничении. Страна офиса и временный work-from-anywhere не доказывают разрешение постоянного трудоустройства; сохранять modes и eligible_countries по прежним правилам. Краткие ограничения показываются лишь для связанной открытой целевой вакансии; ссылка scope.job_url обязательна.
- **AN02/AN03/P03_PUBLIC → Аналитика:** embedded/центральная модель, связь с Product, отдельные DE/AE/DS, явно раскрытые численности и приоритизация. Примеры: `Science & Analytics 6+ / Data 40+`, `Есть DE / AE`, `Совместное планирование с PM`, `Приоритет по business impact`. Не выводить embedded из одного упоминания PM, прямое подчинение из взаимодействия с VP, качество команды из headcount. Численности имеют границы команды и дату в полном ответе/источнике.
- **B06 → Описание бизнеса:** метрика масштаба с единицей и периодом: `40 млн активных участников/год`, `250 тыс. компаний-клиентов`, `5 млрд изображений/год`. Зарегистрированные пользователи, загрузки, устройства, охват, MAU и операции различаются. При неизвестном периоде активности оставить это ограничение прямо в кратком факте. Публичное заявление работодателя не становится независимым замером. Дата публикации и дата чтения различаются в подсказке.
- **T08_INFRA → блок Инфраструктура в Аналитике:** по прежней структуре value.tags и assessments; кроме инструментов выбирать конкретные задачи/ограничения: `Миграция DWH`, `Единые метрики · развитие`, `Контроль качества`, `Ограниченный compute`. Действует/строится/планируется — разные факты. Оценки зрелости требуют отдельного basis. Новое short_facts здесь не заменяет прежнюю структуру.
- **P07_INTERVIEW → плашка Интервью:** заполнять прежние stages/assignment. UI сам добавляет take-home/live case/без тестового из проверенного assignment.kind; длительность — только явно опубликованные трудозатраты, не дедлайн. Разные форматы по разным ролям остаются различимыми в модалке; неизвестное не означает отсутствие задания. Не создавать отдельные теги по поисковому snippet или общему footer.
- **A07_SALARY_BENCHMARK → Информация:** прежний salary web research; компонент, статистика, валюта/период, точная роль/страна, source_updated_at, N и область выборки. Краткую сумму UI форматирует сам. Смежная роль видна на плашке; N, даты, ограничения и ссылка — в подсказке и полном ответе. Не подставлять TC вместо base или зарплаты вакансии.

Роль, страна, дата проверки и URL принадлежат исходному observation и доступны при наведении/клике. Не добавлять «· роль» ко всем тегам; значимое ограничение самой формулировки (B2B, только ES, смежная DS) нельзя спрятать целиком в tooltip.

## Сохранение и приоритеты

Сначала сохранить содержательный полный ответ, затем написать короткую формулировку на основе прочитанного. Если нового материала нет, допускается сократить уже проверенное observation, сохранив value/scope/evidence и даты источников; это не новый сетевой мониторинг. Использовать прежний preview/import/review, без удаления истории и без продления возраста evidence. Устаревшие/непроверенные ответы остаются во «Всей информации», но не становятся текущими краткими преимуществами.

На экране места мало: выбирать отличительные задачи, ограничения и устройство работы; общие SQL/Python и data-driven не должны вытеснять особенности роли. UI ограничивает количество плашек и открывает остальные через +N. Не заполнять все возможные short_facts ради количества. WLB, стабильность и «сильная команда» не следуют из рекламного текста, раунда или названий инструментов. При текущем сценарии новые финансовые/репутационные плашки не вводятся.
