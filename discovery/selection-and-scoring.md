# Профиль, сводки и пригодность компаний

Основной результат исследования виден в «Сравнении компаний». Задача — помочь решить, почему среда интересна, какую роль смотреть и что уточнить следующим.

## Профессиональное ядро и доступность

Читай `jobs_profiles.selection`: `core`, `coreVersion`, `scenarios`, `activeScenarioId`. `profiles` — исходные записи для совместимости и истории, не список независимых персон. Ключевые приоритеты живут в core, не дублируются в скиллах. У пользователя приоритет зрелой среды и сильных коллег; практика нужна преимущественно для интервью.

Для поиска, monitoring, company list/profile/plan передавай `scenarioId`: ID выбранного сценария либо `all` для поиска без географических ограничений. Поиск без явного ID использует активный сценарий. Мониторинг без override использует `source.scenarioId`, затем сценарий прежнего `source.profileId`, иначе `all`. Старые source/profile IDs сохраняются. Проверяй эффективный контекст в ответе. Не подменяй глобальное ядро ради одного запроса и не считай Remote разрешением работать из любой страны.

Текущее семейство ролей включает профильные Product/Data Analyst, Product/Insights/Decision Data Scientist и Analytics Lead, если они выбраны в ядре. Название — предварительный отбор: уточняй ежедневные задачи по полному тексту. Неизвестный грейд/география сохраняются как кандидаты на проверку. По одной SQL-компетенции нерелевантная роль не становится целевой. Не обещай подтверждённую доступность при неизвестных визе, языке или компенсации.

Изменение настроек — только в рамках запроса пользователя: `jobs_selection_update` с текущим `expectedVersion`. Не удаляй сценарий, выключай `enabled`; история и привязки источников сохраняются. Версия ядра меняется только при правке core, смена географии не делает оценку культуры устаревшей.

## Быстрый разбор и углубление

Для быстрого отбора прочитай сохранённые материалы, полное JD и один наиболее полезный источник о практике. Приоритетные вопросы: как аналитик влияет на решение; есть ли цикл измерения с review; с кем можно обсуждать методологию; сколько работы уходит на отчётность/поддержку; есть ли профильная роль и значимый барьер доступности. Не заполняй весь registry перед первым выводом.

Для перспективных компаний углубляй решающий пробел: кейс «гипотеза → метод → решение», процессы команды, профессиональный опыт непосредственных коллег, качество данных/DE/AE support. Слабые источники не компенсировать количеством. Инженерный блог о ML serving не доказывает культуру продуктовой аналитики. Старый кейс сохраняет дату и историческую ценность, без объявления его текущей практикой. JD — заявленные обязанности, не доказанная реализация. Для реальных внутренних условий готовь адресные вопросы интервью.

## Первые предложения

**Бизнес:** 1–2 предложения: покупатель и продукт → за что платят/как устроена экономика → интересная аналитическая задача, если она подтверждена. Без общего «инновационная технологическая компания» и каталогов направлений группы.

**Аналитика:** 1–2 предложения: какую работу здесь делает аналитик → сильнейшее подтверждённое основание пригодности → существенная неопределённость. Например: «В роли заявлены ownership метрик и дизайн экспериментов с PM. Это близко к профилю; регулярность review и сила команды пока не подтверждены». Это пример формулировки, не готовый факт о работодателе.

Сводка пишется последней, из сохранённых атомарных observations. Нельзя объединять практики разных ролей/стран в воображаемую идеальную команду. Укажи scope выбранной роли; общие факты можно дополнить более узкими, но вывод остаётся узким. Предыдущее исследование не стирать. Бизнес и аналитика в новом assessment имеют собственные `evidenceIds`; summary не создаёт новую верификацию.

Теги — 3–4 различающих факта: задача, механизм культуры, среда/инструменты, условия. «Эксперименты» и «A/B testing» — синонимы; «A/B platform» — отдельное более сильное утверждение, требует прямого источника. Публикации коллег — повод изучить их работу, не автоматический высокий балл команды. Не заполняй теги словарём из требований вакансии.

## Оценка

Для независимого исследования культуры применяется [методика компании и команд v2](culture-and-team.md) и `jobs_company_culture_assess`. Историческая экспертиза сохраняет балл, актуальность отражается отдельной уверенностью. Ниже — совместимый прежний формат v1: он остаётся для старых оценок, но не заменяет новый разбор. Правило истечения оснований ниже относится к v1.

После сохранения и review фактов вызови `jobs_company_assess({companyId,assessment})` в рамках авторизованного исследования. Если новая MCP-схема ещё не доступна, эквивалент — `POST /api/company-research/:id/assessment`. Контракт: [shared/company-fit.ts](../shared/company-fit.ts), пример ниже.

Шесть измерений: `influence`, `experimentation`, `peers`, `data`, `product`, `automation`. Веса читаются из core. Оцени каждое один раз: 0 — подтверждённая неблагоприятная практика, 1 — эпизодическая, 2 — базовая, 3 — устойчивый процесс с примером, 4 — сильная системная практика с применением и обратной связью. Неизвестное — `rating:null`, `basis:unknown`, короткое объяснение пробела. Одни требования вакансии (`role_requirement`) ограничены 2. Доказанный процесс — `practice`; это ответственность исследователя за содержание, а не ярлык, позволяющий повысить оценку.

Каждый ненулевой и нулевой rating ссылается на свежие reviewed observations этой компании, совместимые со scope. Не ставь 0 за отсутствие упоминания и не назначай 4 за название технологии. Не учитывай один сигнал дважды в разных измерениях без отдельного объяснения. Для peers нужны реальные возможности совместной работы/review, для data — продуктивная работа и поддержка, а не наличие Snowflake. Для product — сложность и наблюдаемость задач, а не личная симпатия B03.

Итог — сумма `weight × rating / 4`, нормированная на изученную часть до 100. Всегда читай рядом coverage, диапазон возможного результата и provisional. Это пригодность среды для ядра, не вероятность оффера и не итог доступности конкретной вакансии. Старые boolean-факты дают лишь осторожную предварительную оценку. Новый assessment добавляется в историю. После изменения ядра, истечения/отзыва оснований оценку нужно пересмотреть.

## Очереди

Рекомендация Target: Q≥80, покрытие ≥60%, свежий содержательный assessment; при включённом приоритете зрелой среды эксперименты/методы и коллеги должны иметь ≥3. Неизвестное направляет в исследование. Эти пороги — прототип для калибровки; личный priority не меняется автоматически. Хорошая среда без вакансий остаётся в наблюдении.

Практика — отдельная цель, без диапазона Q и требования принять оффер. Сравнивай сходство этапов с целевыми интервью, актуальный пробел (SQL, product sense, statistics, English, leadership), сложность и время. Сохраняй `practiceGoal`, `practiceHours`, `practiceReflection` через preferences в рамках запроса. Успех — обнаруженный и закрытый пробел, не количество офферов. Не предлагай наиболее желанные Target-компании первыми для разминки по умолчанию. Неизвестная компания не считается «средней».
